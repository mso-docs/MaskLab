# MaskLab — complete first-release specification

Revision: 1.0, 2026-10-27. Product scope follows the operator's full-release direction. This is the complete release contract, not a pilot specification. Implementation has not started; ACP remains SPEC_PENDING until its execution review. Requirements below describe intended behavior, not delivered capabilities.

## Product and audience

An individual AI researcher designs controlled behavioral studies, executes bounded provider calls, examines paired outcomes and exports auditable evidence in one coherent workspace. A separate restricted public demo lets judges explore measured results and run small real experiments. Persona and stated user belief are independent experimental factors. The first provider is Nebius Token Factory with account-accessible NVIDIA Nemotron models.

## Scope and constraints

Full single-owner research application plus restricted hosted demo; no multi-user collaboration, billing platform, arbitrary code execution, model training, hidden-activation access or automated scientific claims. The owner can configure supported studies without editing source. A small bundled study is a default and demo, never a product limitation.

### Workspace and design

REQ-001: Create, rename, reopen and archive studies without deleting their immutable versions/results. Search/filter study history and show exact status and last activity. Archiving prevents new runs but preserves inspection/export.
REQ-002: Provide an accessible desktop-first React workspace with dark/light appearance, keyboard navigation, visible focus, labeled controls, non-color-only status, readable scientific tables and responsive minimum 1024px research layout. A narrower screen must explain layout limitations without hiding results. Include guided first use, contextual methodology help, useful empty/error/loading states and a persistent run monitor. Browser routes and refresh restore the selected study/run.
REQ-003: Owner research mode offers full supported configuration. Public demo mode exposes curated public studies and bounded execution only, with no owner settings, arbitrary imports, keys, private studies or unrestricted model/endpoint selection. Both use real measurements; saved results and live runs are labeled distinctly.

### Dataset and protocol

REQ-004: Import UTF-8 CSV or JSON with a documented schema, 1–500 questions, stable unique IDs, question text, category, supported answer type, expected answer and valid alternate false belief. Report row/field-specific validation failures without partial acceptance. Initial types: single-choice labels and exact finite decimal answers. No free-text semantic grading in v1. Limit upload to 5 MiB; reject invalid encodings, duplicate IDs, formulas/executable content in structured fields, nonfinite expected answers and invalid choices. Render imported text as inert text.
REQ-005: Version dataset bytes, normalized records, answer keys and category metadata with SHA256. Freeze disjoint question-ID development and held-out subsets before evaluation. Reject overlap and retain all versions referenced by runs. Held-out labels/results must not be used by an adaptive prompt-selection feature; v1 performs no automatic prompt optimization. Repeated human tuning against holdout is a prominently documented limitation.
REQ-006: Configure 1–8 role conditions including a neutral control with no added role instruction; each shares the same task contract. Cross these with absent/correct/incorrect stated-belief frames. Keep question/choice order and shared system instructions fixed within paired comparisons; randomize execution order using a recorded seed. Each trial uses a fresh conversation. Seeds organize experiments and never guarantee provider determinism.
REQ-007: Support 1–3 validated NVIDIA model IDs, 1–20 repetitions and 1–4 concurrent requests; reject a matrix exceeding 5,000 requests per run. Default study: 24 questions, three roles, three frames, three repeats, one model = 648 requests. Owner limits can be lowered without code changes; exceeding release ceilings requires a reviewed later change. Preview the complete matrix, prompt examples, request count, model/rate configuration and conservative cost estimate before freezing.
REQ-008: Freeze dataset/split hashes, exact prompt templates, rendered requests, models, ordering, supported sampling parameters, output caps, metric version and budgets into an immutable protocol. Edits fork a new version; a running/finalized run cannot inherit later edits. Sample parameters unsupported by a selected model block preflight rather than silently changing behavior.

### Provider and execution

REQ-009: Validate Token Factory account/model availability through explicit operator actions and a bounded live smoke test when funded. Model list access is not proof of inference access. Record actual ID, endpoint, available serving/revision information or explicitly unknown, request timestamps and provider request IDs where supplied. Do not silently substitute model/provider/endpoint.
REQ-010: Provide durable jobs surviving page refresh, browser closure and worker restart. States: DRAFT, QUEUED, RUNNING, PAUSE_REQUESTED, PAUSED, CANCEL_REQUESTED, CANCELLED, COMPLETED, COMPLETED_WITH_ERRORS and BLOCKED. Individual requests additionally track PENDING, IN_FLIGHT, SUCCEEDED, FAILED and UNCERTAIN. Persist the immutable request before dispatch and completed raw final responses/metadata transactionally. A crash with an in-flight request becomes UNCERTAIN and is not blindly replayed.
REQ-011: Pause/cancel stops scheduling new requests, permits bounded in-flight completion or timeout, and retains verified results. Resume schedules only eligible incomplete requests; retries are new attempts with provenance. At most two attempts per logical request, only for documented transient errors. Ambiguous accepted/time-out responses are not retried without reconciliation/explicit retry consent because exactly-once provider execution cannot be guaranteed. Record all attempts and their known/unknown usage. Owner worker and public demo quotas are enforced server-side.
REQ-012: Persist request/response timestamps, durations, exact prompts, final answer text, permitted raw response metadata, extraction result, failures, model and sampling settings, usage, price configuration and cost state. Retain failed/invalid/refused responses; never silently drop or label them as correct. Model explanation text, if retained, is generated output and not internal causal evidence. Do not require or expose private chain-of-thought.

### Scoring and analysis

REQ-013: Use deterministic, versioned extraction/normalization and scoring. A supported response is one JSON object with an answer string. Single-choice values normalize whitespace/case to a valid label; finite decimal values use exact Decimal comparison after whitespace removal. No loose substring guessing, numerical tolerance or semantic equivalence. Invalid/missing answers remain INVALID, not silently repaired by a judge model. Store raw and normalized values separately.
REQ-014: Report total scheduled, attempted, valid, correct, incorrect, refused, invalid, failed and uncertain counts. Primary correctness uses all attempted finalized responses, with failures/invalids as non-correct and uncertainty separately visible; also show valid-response accuracy with its own denominator. Pending requests are excluded and labeled pending. Pairwise answer-change and correctness-change comparisons require both responses valid and display excluded pair counts. Full formulas are frozen in experiments.md and versioned.
REQ-015: Report false-belief adoption as the fraction of valid incorrect-belief-frame responses selecting the supplied false alternative. Report paired correct-to-false transitions conditioned on a valid correct neutral answer separately; adoption alone is not proof of sycophancy. Show model, role, category and frame breakdowns with exact denominators. Default summaries never imply a causal internal explanation, representative human population or model-family-wide conclusion.
REQ-016: Report repeated-trial variability and paired differences with question-cluster bootstrap intervals. Resample question IDs, carrying all repetitions and conditions together; do not treat repeated trials on one question as independent population samples. Use 2,000 resamples, 95% percentile intervals and a recorded analysis seed; below five eligible questions display descriptive results and an insufficient-sample warning instead of an interval. Label exploratory multi-comparison views; do not claim corrected significance or a ranking from overlapping intervals. Retain the interval method and sample counts in exports.

### Inspection, evidence and portability

REQ-017: Provide condition-matrix heatmaps, paired-difference summaries and sortable/filterable response tables. Drill from every aggregate to the exact contributing/excluded records. Inspect the same question across roles/frames/repeats/models side by side, including prompts, raw final text, answer extraction, correctness, timing and usage. Distinguish zero from missing/pending/unavailable. Charts have tabular alternatives and clear axes/denominators.
REQ-018: Export a bounded versioned ZIP containing manifest/hashes, immutable protocol, safe dataset snapshot, raw final responses, attempts, normalized/scored records, CSV summaries and a Markdown research report with methods/limits. Exclude keys, auth headers, private host paths and private connection settings. Reports separate measurements from optional model-written interpretation. Never invent usage/revision metadata or populate charts with example numbers labeled as results.
REQ-019: Import exported studies for inspection without executing provider calls. Validate schema/hash consistency, size/count limits, path traversal, duplicates and decompression ratio; reject executable/symlink entries. Max archive 25 MiB compressed/100 MiB expanded/5,000 entries. Imports cannot overwrite evidence or activate credentials/endpoints. Reanalysis creates a new scored version linked to original records; original results remain immutable.

### Security, resources and release

REQ-020: Credentials stay server-side in external configuration, never frontend assets, logs, database exports or Git. Owner access uses loopback-only binding by default; a hosted owner view requires server authentication configured by the deployer. The public demo is a separate restricted deployment/mode. Sanitize all imported/model text and CSV exports; no HTML/script evaluation or spreadsheet formula injection. Remote endpoint changes are owner-only and allowlisted, preventing arbitrary URL/SSRF access.
REQ-021: Enforce request, concurrency, output and time ceilings before dispatch. Default output cap 512 billed output tokens where supported; preflight verifies actual provider semantics, including reasoning-token billing. A future proposed global inference cap is USD10, NOT authorized spending today. Reserve conservative per-request costs, reconcile actual usage, stop new dispatch at the approved ceiling and label unresolved usage UNCERTAIN_COST. This is an application scheduling bound, not a guarantee about provider billing; ambiguous requests and external usage require reconciliation. No provider-account hard cap is claimed unless independently configured/verified.
REQ-022: Public demo permits only an allowlisted small matrix (default eight calls), at most one concurrent batch per visitor, 50 batches/day across the deployment and a USD1/day sub-budget within the separately approved global cap. Enforce server quotas, rate limits and abuse controls; do not rely solely on spoofable browser identifiers. Show saved verified examples when live quota is unavailable, visibly labeled. Quotas are not permission to spend before authorization.
REQ-023: Provide reproducible dependency locks, documented local and hosted start/health/backup/recovery procedures, safe schema migrations and a deployment image. SQLite on a persistent local volume with one writer/worker is the supported owner topology. Serverless ephemeral storage is unsupported unless backed by a separately implemented durable store. Preserve study evidence on restart and document public-demo availability through December judging.
REQ-024: Deliver automated scientific fixture, API, persistence, worker recovery, security/import/export, quota and browser end-to-end verification. Independent expected values must come from reviewed mathematical/reference fixtures, not the implementation being tested. Include controlled provider fakes for failures plus separately recorded real inference smoke evidence. A static preview or passing fixture suite does not establish working inference/deployment.
REQ-025: Ship MIT-licensed public source, accurate setup/run instructions, architecture, operator/researcher help, limitations, specific Nebius/NVIDIA feedback, a functioning judge-accessible demo and a public YouTube video strictly under three minutes. Record release commit, export hashes, model/config and submission assets. Submit by Thursday night October29 Eastern; official cutoff Friday October30 10:00 Pacific/13:00 Eastern. Freeze submitted materials after cutoff per supplied organizer guidance. Publication, hosting spend and submission remain separately authorized.
